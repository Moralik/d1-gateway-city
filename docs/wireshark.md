Часть 3. Третья попытка: клиент не доверяет УЦ
Описание Alert: Level = Fatal, Description = Unknown CA.
Отправил клиент (10.99.0.7:52002), потому что у него нет корневого сертификата city-root.crt и он не может проверить цепочку доверия сертификата сервера.
Если бы клиент был запущен с curl -k, проверка сертификата была бы отключена, соединение установилось бы успешно и Alert не был бы отправлен.
Чтобы посредник прошёл незамеченным, достаточно добавить его корневой сертификат в хранилище доверенных сертификатов клиента.
В коде это одна строка — указать путь к сертификату посредника как к доверенному CA:
curl (C): curl_easy_setopt(curl, CURLOPT_CAINFO, "mitm-ca.crt");
Python (requests): requests.get(url, verify="mitm-ca.crt")
Или полностью отключить проверку:
curl (C): curl_easy_setopt(curl, CURLOPT_SSL_VERIFYPEER, 0L);
Python: requests.get(url, verify=False)
Суть: клиент перестанет отвергать сертификат посредника, если тот добавлен в список доверенных или проверка отключена.

Часть 4. Расшифровка своими ключами
Вопрос 9
Wireshark взял ключи из файла 02_bank_https_keys.log, указанного в настройках TLS. Этот файл содержит traffic secrets (симметричные ключи сессии), которые клиент записывает при установке переменной SSLKEYLOGFILE. Файл такой же секрет, как пароль, потому что с его помощью можно расшифровать весь трафик сессии (включая логины, пароли, cookie), даже без закрытого ключа сервера.

Вопрос 11
Нет, не получится. В TLS 1.3 используется ECDHE (эфемерный Diffie-Hellman), обеспечивающий прямую секретность (forward secrecy). Симметричный ключ сессии вычисляется из одноразовых ключей DH, которые генерируются заново для каждой сессии и не сохраняются. Закрытый ключ сервера используется только для подписи параметров handshake (аутентификация), но не участвует в вычислении общего секретного ключа. Поэтому без файла SSLKEYLOGFILE расшифровать трафик TLS 1.3 невозможно, даже имея закрытый ключ сервера.
